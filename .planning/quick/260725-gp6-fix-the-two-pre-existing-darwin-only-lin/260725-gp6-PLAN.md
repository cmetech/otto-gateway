<analysis_findings>
Planner verified both findings against the source before writing this plan.
The executor should treat these as established, not re-derive them:

**Finding 1 — `unparam` on `runOpenDesktopFolder`'s `goos` is a per-GOOS false
positive. Do NOT delete or hardcode the parameter.**
- `openfolder.go` is tagged `//go:build darwin || windows`.
- `goos` is consumed at `openfolder.go:135` (`appFolderTarget(goos, ...)`) and
  `openfolder.go:138` (`resolveHermesHome(goos, ...)`). Both branch on
  `goos == "windows"` (`openfolder.go:40`, `:52`, `:71`). Removing the parameter
  would silently break the windows arm's folder resolution.
- The only non-test caller is `handleOpenDesktopFolder` (`openfolder.go:161`),
  which passes `runtime.GOOS` — a per-build constant. Under `GOOS=darwin`,
  `unparam` sees the single value `"darwin"`. Under `GOOS=windows` the same call
  site yields `"windows"`.
- The three test call sites (`openfolder_test.go:196, 231, 240`) all pass the
  literal `"darwin"`, which reinforces the constant-value inference on this box.
- Conclusion: the parameter is load-bearing and is also the test injection seam.
  The fix is a justified nolint, matching the existing repo idiom
  (`cmd/otto-tray/paths.go:59` already uses `//nolint:unparam` with an inline
  justification; `desktop_darwin.go:20` and `openfolder_windows.go:19` use the
  same shape for gosec).
- Considered and rejected as out of scope: adding a `"windows"` test call site to
  give the parameter two observed values. It depends on unverified analyzer
  behavior around test files and widens the diff beyond the two findings.

**Finding 2 — `wrapcheck` on `desktop_darwin.go:28` is genuine and safe to fix.**
Every consumer of that error was checked:
- `platformDesktopRunning` → `desktopRunningFn` → `isDesktopRunning`
  (`desktoprun.go:9,13`).
- `desktoptray.go:242` and `:265` only interpolate `err.Error()` into a
  notification body and a `desktopOutput.Detail` string. No `errors.Is`, no
  `errors.As`, no substring matching on the message.
- `openfolder.go:107-109` wraps it as `fmt.Errorf("%w: %w",
  errDesktopRevalidation, err)`; the only sentinel check
  (`openfolder.go:180`) tests `errDesktopRevalidation`, which is unaffected.
  `%w` preserves the chain regardless.
- No test constructs, asserts on, or reaches the pgrep error: there is no
  `desktop_darwin_test.go`; `desktoprun_test.go` and `desktoptray_test.go` both
  replace `desktopRunningFn` wholesale with their own stub, and
  `openfolder_test.go` asserts `errors.Is` against its own injected error.
- Net user-visible effect: notification/Detail strings gain a `pgrep: ` prefix,
  which is the desired operator context.

**Why no `tdd="true"` block despite `workflow.tdd_mode: true`:** neither change
has a testable new behavior surface. Task 2 is an annotation only. Task 1's
changed line is only reachable when the real `pgrep` binary exits with a code
other than 0 or 1; `platformDesktopRunning` shells out directly with no
injectable command seam, and any new test would have to be `//go:build darwin`
tagged, so CI (ubuntu) would never run it. Per the task constraint, a test is
added only if the package's existing style supports it without new scaffolding —
it does not. The existing suite is the regression gate instead.
</analysis_findings>
